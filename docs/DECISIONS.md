# Decisions

Record every important decision here: what you chose, what else you considered, and why.

## D1 — Stack (Day 1)
- Frontend: React (TypeScript, Vite)
- Backend: Go (REST API)
- Database: PostgreSQL
- Hosting / run: Docker Compose (`docker compose up` starts db, backend, frontend)
- Why: Go gives a simple, fast, strongly typed API with explicit SQL and transactions, which fits stock reservation and balance math. React is the UI stack the team knows best. PostgreSQL has real transactions and row locking, needed to prevent double reservation and negative stock. Docker Compose gives one documented command on a fresh clone.
- Considered: Node + React (one language, but Go gives a typed, explicit backend), Next.js full-stack (less setup, but blurs the frontend/backend split and review ownership), SQLite (no setup, weak under parallel writes), MySQL (works, but Postgres is the better fit in the Go ecosystem).

## D2 — Auth approach
- Email + password. `POST /auth/register` creates the seller and their shop in one transaction and returns a token; `POST /auth/login` returns a token. Password 8–72 bytes (bcrypt reads only 72), stored as a bcrypt hash; email trimmed and lower-cased; shop name 1–120 characters. Spaces around the password are dropped at sign-up and at login, before the length check: a pasted password with a leading space was refused with no visible reason. Spaces inside it are kept. A password saved with surrounding spaces before this rule no longer works, which is accepted while there are only test accounts.
- Token: JWT signed with HS256 and `JWT_SECRET`, lifetime `JWT_TTL` (default 24h), carrying `seller_id` and `shop_id`. Sent as `Authorization: Bearer <token>`; only HS256 is accepted, expired or foreign tokens get `401 unauthorized`.
- `auth.RequireAuth` checks the token and puts the principal in the request context; handlers read the shop only from there (`auth.MustPrincipal`), never from the body or URL. Every repository filters by that `shop_id`, so another seller's data is `404`.
- Wrong password and unknown email both answer `401 invalid_credentials` and take about the same time (a dummy bcrypt compare), so the API does not reveal which emails exist. A taken email is `409 email_taken`.
- Logout is client-side: the frontend drops the token. No server session store. The frontend will keep the token in `localStorage` (ARCHITECTURE open question 1, a known trade-off).
- Why: works without any outside service, is easy to test, and fits a 3–5 day MVP; one token per seller already scopes every request to one shop.
- Considered: phone + one-time code (needs an SMS provider and rate limiting), server sessions with cookies (state on the server, CSRF handling), refresh tokens (more moving parts than an MVP needs; a seller logs in again after 24h).

## D3 — API contract format
- The contract is OpenAPI 3.0 in `api/openapi.yaml`. It is the single source of truth for paths, request and response schemas and error cases; field names equal the JSON tags in Go.
- Every new or changed endpoint is described in the same PR as its code (AGENTS.md). Swagger UI at `/docs/` (open, no login) shows the file; `npx @redocly/cli lint api/openapi.yaml` validates it.
- Shared conventions live in the file once: Bearer auth, `snake_case` JSON, money as integer so'm, `?page=&page_size=` lists returning `{items, page, page_size, total}`, and errors as `{code, message}` with the codes from backend/AGENTS.md.
- The frontend will generate its API types from this file (`frontend/AGENTS.md`), so the client cannot drift from the backend.
- Why: frontend and backend can work in parallel against one agreed contract, reviewers see API changes as a diff, and the docs page comes for free.
- Considered: a shared TypeScript types package (no docs page, Go side still hand-written), a markdown table in the README (drifts silently, no validation), GraphQL / tRPC (new tooling for the team, tRPC needs a TypeScript backend).

## D4 — Branching & merge rules
- Never commit directly to `main`. Every change is an issue, a branch and a pull request.
- Branch name: `<type>/<issue-number>-<short-name>`, for example `feat/12-product-list`, `fix/31-stock-negative`, `docs/4-branching-rules`. Types: `feat`, `fix`, `docs`, `chore`, `test`, `refactor`.
- Commits follow Conventional Commits: `feat:`, `fix:`, `docs:`, `chore:`, `test:`, `refactor:`.
- Pull requests: one issue each, aim for fewer than 400 changed lines, use the PR template, link the issue with `Closes #N`, add a screenshot or short video for any UI change.
- Review: at least 1 approval from a teammate, never the author. Comments must be specific, not only "LGTM". The author fixes comments on the same branch.
- Merge: only when CI is green and the PR is approved. Use squash and merge, then delete the branch. The author merges their own approved PR.
- Merge captain: one person per day, rotating, listed in `TEAM.md`. Watches the board, unblocks reviews and keeps `main` releasable.
- Stuck for more than about 1 hour: ask a teammate or pair up.
- Why: small reviewed PRs keep `main` working for the whole team changing the same repo, and the history shows who did what.
- Considered: trunk-based direct commits (faster, no review trail), long-lived feature branches (big merges and conflicts).

## D5 — Stock
- Own package `backend/internal/stock`, separate from `product`, because Stock and Products have different owners (`TEAM.md`). It writes only `stock` and `updated_at` of the `products` table and reads `reserved` and `status`; the table itself comes from the products migration.
- `available = stock − reserved`. Label: `out_of_stock` when available is 0, `low_stock` when 0 < available ≤ threshold, `in_stock` otherwise. `PATCH /products/{id}/stock` answers with the product, like every product endpoint (D14), and a product carries no `available` or `stock_label` (D13): a screen computes `available` from `stock` and `reserved`.
- Low-stock threshold: not a backend setting any more (D16). The backend returns only `stock` and `reserved`; the screen derives `available` and the warning, with its own threshold.
- Manual change: `PATCH /products/{id}/stock` with `{"stock": 12, "expected_stock": 10}`, behind auth. `stock` is the new absolute quantity, not a delta, so a retried request gives the same result. Rules: integer 0–1 000 000; not below `reserved` (`409 stock_below_reserved`, the seller cannot take back goods promised to accepted orders); archived products cannot change (`409 product_archived`); another shop's product is `404 not_found`. Response: `{product_id, stock, reserved, available, stock_label, updated_at}`.
- `expected_stock` (required) is the stock the seller saw before editing. If it no longer matches (another tab, an order), nothing is written and the answer is `409 stock_changed`; the UI reloads the product and shows the real number. Error bodies are the shared `{code, message}` (backend/AGENTS.md).
- The rules are in one `UPDATE … WHERE` statement, so a concurrent order accept or a second tab cannot slip between a check and the write.
- Orders declare a small interface that `stock.PgRepository` implements (ARCHITECTURE rule 4): `Reserve` (accept), `Release` (cancel) and `Commit` (deliver), passing their transaction (`database.DBTX`), one item at a time in ascending product id to avoid deadlocks. `Reserve` cannot oversell (`stock − reserved >= qty` in the `WHERE`) and returns `ErrInsufficientStock`; `Release`/`Commit` return `ErrReservationMismatch` if fewer units are reserved than the order holds, so the order transaction rolls back.
- Why: one owner per feature, one place for stock math, no silent lost updates, and the database `CHECK` constraints stay the last line of defence.
- Considered: stock inside `product` (one package, but two owners editing it), delta updates `{"change": -2}` (shorter for +/- buttons, but a retried request would apply twice), last write wins without `expected_stock` (simpler, but one tab silently overwrites another), per-shop threshold (more settings UI for little MVP value).

## D6 — Rate limiting
- Four layers, no Redis. Nginx (shared by every client of the stack): `/api/` limited to 10 requests per second per IP with a burst of 30, and `/api/auth/` to 10 per minute per IP with a burst of 5. Backend: `httpx.RateLimit`, a token bucket per key, for protected routes per shop (`RATE_LIMIT_SHOP_RPS` 20, `RATE_LIMIT_SHOP_BURST` 40), plus a login guard.
- Login guard: 5 failed attempts per IP and email in 15 minutes (`RATE_LIMIT_LOGIN_ATTEMPTS`, `RATE_LIMIT_LOGIN_WINDOW`), then `429` until a token refills (one per 3 minutes). Only failed attempts count and a successful login resets the counter. While blocked, even the right password is refused, so guessing cannot win on attempt 6. The key includes the IP so a stranger cannot lock a seller out of their account from another network.
- Answer: `429` with `Retry-After` and `{"code":"rate_limited","message":"..."}`, the same shape from nginx and from the backend.
- Client IP: the backend uses `X-Real-IP` only when the request comes from a trusted proxy (`TRUSTED_PROXIES`, default loopback and private ranges, which covers the nginx container). Any other client cannot spoof its address with a header.
- Limits live in process memory and idle keys are swept every minute. They reset on restart and are counted per backend instance. That is fine for one instance. If the backend is scaled out, move the counters to Redis.
- Why per shop and not per IP for protected routes: sellers behind one office or mobile network share an IP, a shop ID is the real unit of fairness. Per IP stays at the nginx edge, where no token exists yet.
- Why not a rule per endpoint: new endpoints get the global and per shop limits without anyone remembering to add them. Only the two routes with a real abuse case (login, register through `/api/auth/`) get a stricter rule.
- Not included: CAPTCHA, permanent account lock, Redis.

## D7 — Balance
- Read only. The order feature writes the entries when an order becomes `delivered`: `sale` (+total) and `commission` (−total × `COMMISSION_PERCENT` / 100, integer division), in the same transaction as the status change. `payout` exists in the model; the MVP never creates one.
- `GET /balance`: `available` = sum of all entries, `earned` = sum of `sale`, `commission` = sum of `commission` (negative). One `SUM … FILTER` query; a shop with no entries gets zeros, not 404.
- `GET /balance/entries`: newest first (`created_at DESC, id DESC`, so equal times keep a stable order), `?page=&page_size=` clamped like product lists (default 20, max 100), `items` is `[]` when empty.
- Both routes are protected and filter by the shop from the token; another shop's entries are never visible.
- The `balance_entries` table comes from migration `0004_balance_entries` (Balance), in the shape of `backend/docs/schema.dbml`. The foreign key `order_id → orders` arrives with migration `0005_orders`, because the orders table did not exist when Balance was built. The unique key `(order_id, type)` and the sign checks protect the money: one sale and one commission per order, and a payout never has an order.
- Why compute totals on read: entries are append only and few per order, the sum is one indexed query, and there is no stored total that could drift from the history.
- Considered: a stored running balance on `shops` (faster for huge histories, but two places to keep in sync), net per order instead of separate entries (simpler table, but loses the commission line the seller wants to see).

## D8 — Orders
- Package `backend/internal/order`: list, detail and `POST /orders/{id}/transition`, all behind auth and filtered by the shop from the token. Another shop's order is a `404`, like a missing one. Orders are created by the dev endpoint `POST /dev/simulate-order` (only when `APP_ENV=development`; in production the route is not registered, so it is the JSON 404) and later by the seed script, never by the seller. It picks 1 to 3 active products with available stock, a quantity of at most 3 and at most the available units, and a fake buyer; it reserves nothing, accepting does. With no such product the answer is `409 no_products_to_order`.
- A transition is one transaction: `SELECT … FOR UPDATE` on the order row, the status machine from `DOMAIN.md` checked in the service, the stock effects, the balance entries, the history row and the status update. Any error rolls everything back. Two simultaneous requests for the same order cannot both succeed: the second one waits for the lock, sees the new status and answers `409 invalid_transition`.
- Stock effects are single `UPDATE … WHERE` statements on `products` (the stock rules of D5 stay in one place per statement): accept reserves with `stock - reserved >= qty` in the `WHERE`, so two orders cannot oversell; cancel releases only what was reserved (from `accepted` or `packed`); delivery takes the quantity out of `stock` and `reserved`. The items are locked in ascending `product_id` order so two orders that share products cannot deadlock.
- Accepting does not look at the product status: archiving hides a product from new orders but keeps the reservations of existing ones (D5).
- Delivery writes the `sale` entry (+total) and the `commission` entry (−`total × COMMISSION_PERCENT / 100`, integer division, so it rounds down and no so'm is lost) in the same transaction (D7).
- Every status change writes one `order_status_history` row (`from_status`, `to_status`, `reason`, time) in the same transaction. `GET /orders/{id}` returns them oldest first as `history`, so the order page can show a timeline.
- The first history row of a created order goes from `NULL` to `new`, so every order has a complete timeline.
- `Order.number` is a sequence in the table and the string `#100245` in the API. Prices and titles on the items are snapshots from the time of the order.
- Lists: newest first (`created_at DESC, id DESC`), `?status=&page=&page_size=` clamped like product lists (default 20, max 100); a status that does not exist or a value that is not an integer is a `400`.
- Ownership: the domain code came with Samandar's orders PRs (#71, #76). Nothing was in progress on the PostgreSQL side, so issue #70 was taken over to finish it (repository, wiring, tests); the domain code keeps its behaviour.
- Considered: stock effects through the stock package (one more hop, but the order transaction would need the stock package to accept a transaction), optimistic locking with a version column instead of `FOR UPDATE` (no waiting, but retries and a new column), history as a JSON column on `orders` (fewer joins, but no per-row timestamps or constraints).

## D9 — The spec as JSON
- Swagger UI at `/docs/` only shows `api/openapi.yaml`. Type and client generators and Postman want JSON from a URL, so the backend serves it: `GET /openapi.json`, made from the file in `OPENAPI_FILE` on request (cached by modification time and size, so an edit shows at once and nothing is converted twice). A missing file is a JSON 404 `spec_not_found`, an invalid one a 500 that hides the details and logs them. With `OPENAPI_FILE` empty the route does not exist.
- nginx publishes it as `GET /swagger` and `GET /docs/spec/openapi.json`, and `/api/openapi.json` reaches the same backend route (rate limited like the rest of `/api`). The docs have no login: the basic auth added in #50 was removed (#102) because the team and the frontend developers use the docs and the JSON all the time from several machines. The spec is not secret and the API still needs a token. A public deployment should put its own protection in front of `/docs/`, `/swagger` and `/api/openapi.json`.
- Docker Compose mounts `./api` read-only into the backend too, because the spec lives outside the Go module and cannot be embedded without moving it (it is shared with the frontend generators and Swagger UI).
- Why in the backend and not in the docs container: it is testable in Go (unit and e2e tests), works with `go run`, and needs no extra binary or start script. Keys come out in alphabetical order, which is cosmetic.
- Considered: converting with `yq` when the frontend container starts (works, but needs a binary in the image, a start script, and the JSON goes stale until a restart), baking the JSON at build time (the image is built from `./frontend` and cannot see `api/`), committing a generated `openapi.json` (two copies that can drift), `go:embed` (needs the spec inside `backend/`).

## D10 — Dashboard
- Package `backend/internal/dashboard`, read only: `GET /dashboard/summary` behind auth, filtered by the shop from the token. No new table or migration: the numbers come from `orders` and `order_items` (`0005_orders`), and every query filters by `shop_id`, the first column of the order indexes.
- Business time zone: `BUSINESS_TIMEZONE`, default `Asia/Tashkent` (UTC+5, no daylight saving), loaded once in `config`; an unknown name stops the start. The binary embeds the zone database (`time/tzdata`), so it also works on a machine without one. This answers open question 3 in `ARCHITECTURE.md`.
- Days are calendar days in that zone, not UTC: 01:30 in Tashkent is still yesterday in UTC, and a seller expects their own day. Today is 00:00 to 24:00, "last 7 days" is today and the 6 days before it, "last 30 days" is today and the 29 before it. Bounds are half open (from included, to excluded) and every window ends at the end of today, so an order stamped a little ahead of the app clock is not lost.
- Today's orders: `created_at` today, any status. Waiting for action: `new`, `accepted` or `packed` with no time limit, because an order stuck for weeks is the one the seller must see. `handed_to_courier` is not waiting: the seller's part is done.
- Revenue 7 and 30 days: sum of `orders.total` of `delivered` orders by `status_changed_at` in the window. It is before commission (the balance page shows the net, D7). `delivered` is final, so `status_changed_at` is the delivery time. Cancelled orders are never revenue.
- Top 5: units in orders delivered in the last 30 days, grouped by product; `revenue` is the sum of `price_snapshot × quantity` of those lines. Ranked by units, then revenue, then `product_id`, so the order is stable. `title` is the current `products.title`, the name the seller sees in the product list; archived products stay in the ranking because they were sold.
- A shop with no orders gets zeros and `top_products: []`, not 404 (like D7). The endpoint takes no input, so its only errors are `401` and `500`.
- Two queries (counts and sums in one `FILTER` query, the ranking in another) outside a transaction: a delivery landing between them can show on the sums but not yet in the ranking for one request, which is fine for a home page that is read again on the next visit.
- Considered: rolling 24-hour windows (simple, but "today" would not match the day the seller sees in the order list), UTC days (no config, but orders placed after 19:00 UTC land on the wrong day), a stored daily rollup table or a cache (one indexed scan of one shop's orders is enough for now, measure before adding a second place that must stay in sync), `title_snapshot` in the ranking (matches what was sold, but one product could appear under two names).

## D11 — Seed
- `backend/cmd/seed` is a thin command over `backend/internal/seed`. It runs only when asked, only when `APP_ENV=development` (the demo login is public, so it refuses in production), applies the migrations and then fills an empty database. The Docker image holds the binary: `docker compose exec backend /seed`.
- It writes through the services (auth, shop, product, stock, order), never with hand-written inserts, so the rules of D5, D7 and D8 decide what is possible: a product is reserved when its order is accepted, delivery takes it out of stock and writes the sale and the commission, and every status change has a history row.
- The data is fixed, not random: 15 products (13 active, 1 draft, 1 archived) and 30 orders (4 new, 2 accepted, 2 packed, 3 handed to the courier, 15 delivered, 4 cancelled from `new`, `accepted` and `packed`). Everyone sees the same demo, tests can state exact numbers, and the story is planned: 5 orders today, 8 waiting for action, 6 deliveries in the last 7 days, a top 5 with real differences, one product out of stock and two low on stock (the products get a high stock first and the seller-facing level is set at the end through the stock service).
- Dates are relative to the moment of the run, in the business time zone of D10. The order service got three small additions for this: `WithClock` returns a copy that reads its time from a function, `Place` stores a buyer's order (no route calls it), and balance entries are stamped with the time of the status change instead of the database clock, so the balance history is old too. Each status change of an order is spread over six hours after the placement, but never after a minute before now, so nothing is dated in the future whatever the time of day.
- Order creation now checks that every item is a product of the shop (`ErrProductNotFound` and a rollback otherwise); `Place` is public inside the backend, so it must not trust a product id.
- Running it twice changes nothing: if the demo seller exists the command says so and exits. A run that failed halfway leaves partial data; the fix is an empty database (`docker compose down -v`), because a half-finished state is not worth a second code path.
- Considered: SQL inserts with fixed dates (shorter, but the numbers would stop agreeing with the rules the first time a rule changes), calling the dev endpoint 30 times (every order is dated now, so the dashboard windows and the balance history stay empty), random data (nicer variety, but tests and demos cannot name a number), a `--reset` flag (one more way to delete data by accident).

## D12 — Image uploads
- Package `backend/internal/upload` is the image service the product and shop features use through their own small interfaces; it has no HTTP endpoint (D16). Reading is not an API route: nginx serves `GET /api/uploads/{shop_id}/{name}` straight from the `uploads` volume (mounted read only into the frontend container), so buyers see product photos without a token and the Go process never streams a file. Only paths of the form `<digits>/<32 hex>.webp` are served, everything else under `/api/uploads/` is a JSON 404. Headers: `Cache-Control: public, max-age=31536000, immutable`, `nosniff`, `Content-Security-Policy: default-src 'none'`. The repository is a directory on disk (`FSRepository`, confined with `os.Root`, so `..` and symlinks cannot leave `UPLOAD_DIR`); in Docker it is the named volume `uploads`. No table: the product and the shop store the returned URL as text.
- The pipeline is one function: read at most 5 MB, sniff the type from the bytes (`http.DetectContentType`, never the file name or the client's `Content-Type`), read the size with `DecodeConfig` and refuse more than 20 megapixels before decoding (a small PNG can expand to gigabytes), decode, apply the JPEG EXIF orientation, scale down to 2048 px on the longest side, encode WebP quality 80. Re-encoding drops EXIF and GPS. The stored name is 128 random bits, so URLs cannot be guessed and files never change (`Cache-Control: immutable`).
- Library: `github.com/gen2brain/webp` (libwebp compiled to WebAssembly, run by pure Go), with `golang.org/x/image/draw` for scaling. The standard library cannot encode WebP. Choosing it keeps `CGO_ENABLED=0` and the Alpine image without C libraries. Cost: about 0.5 s and a few hundred MB of garbage per 12 MP photo, so at most 3 images are processed at once; a fourth waits 3 s and then gets `503 busy`. Scaling halves a very large image step by step and finishes with `ApproxBiLinear`, and the EXIF turn runs on the scaled image: the Catmull-Rom kernel used first needed about 250 MB of buffer per photo and three uploads at once got the process killed for memory. The price is a slightly less sharp result.
- Limits, in layers: nginx `client_max_body_size 6m`, per IP `10r/s` on `/api/`, a looser separate zone for downloads (a page with many photos must not trip it), per shop `RATE_LIMIT_IMAGES_PER_MINUTE` (default 20) on `POST /uploads`, `http.MaxBytesReader` at 5 MB + 64 KB for multipart, and the 5 MB check in the service.
- New statuses, on purpose: `413 file_too_large`, `415 unsupported_media_type` (not multipart, or not jpeg, png or webp), `503 busy`. A corrupt image, a missing `file` field or too many pixels is `400 validation_error`. `backend/AGENTS.md` lists them.
- Files and shop directories are written `0644` and `0755`: they are public by design and the nginx user (another uid) must read them. Without nginx (plain `go run` and the Vite dev server) the images are not served, point the dev proxy at a local nginx or the compose stack.
- Product photos: `product_photos` (migration `0006`), up to 5 per product, position 0 is the cover. They are saved by the product endpoints, not by a separate upload call: `POST /products` and `PUT /products/{id}` accept `multipart/form-data` (the fields as form fields, images in `photos`, and on `PUT` `keep_photos` for the current URLs that stay; omitted keeps all, empty removes all). A JSON request still works and never touches the photos. Every product response has `photos` (`[]` when none). Why: the product and its photos are one action, so a failed save leaves no orphan file and a removed photo does not stay on disk, and the frontend sends one request.
- All or nothing, in the product service: fields are validated first, then images are converted and stored, then the row is written in one transaction. When the write fails the new files are removed; when it succeeds the photos that are no longer listed are removed (best effort, a failure is logged and only wastes disk). A crash between the file write and the commit can still leave a file; it stays on disk (D17).
- The product feature never imports `upload`: it declares `PhotoStore` (`Save`, `Remove`) and `internal/app/photos.go` implements it on top of `upload.Service`, translating upload errors into product errors (`413`, `415`, `503`, `400`). `PUT` can keep only URLs that already belong to the product, so a seller cannot attach another file by URL; `POST /uploads` stays for the shop logo.
- A request with images is expensive, so a multipart `POST /products` or `PUT /products/{id}` has its own per shop limit (`RATE_LIMIT_IMAGES_PER_MINUTE`); JSON requests are not counted. nginx accepts bodies up to 27 MB (5 photos of 5 MB), the backend limits each route (1 MB for JSON, 5 MB per photo, 5 photos).
- Not done: per-shop disk quota, object storage (S3). A file that a crash leaves behind between writing it and saving its row stays on disk, nothing sweeps it (D17). `FSRepository` and the nginx location are the two places to replace for S3.
- Considered: `chai2010/webp` and `h2non/bimg` (faster, but need cgo and libwebp or libvips in the image), `disintegration/imaging` (resize only, no WebP encoder), storing the original next to the WebP (doubles disk, keeps EXIF).

## D13 — Simpler product shape
- A product response has `stock` and `reserved` but no `available` and no `stock_label`: they are derived from the two numbers, the stock endpoint still returns them for a stock change, and keeping them on every product made the list heavier than the screens needed. `Product.Available()` is gone from the code.
- A product is always created as a `draft`: `POST /products` (JSON and multipart) takes no `status`, a `status` in the body is `400 invalid_body` (`400 validation_error` in multipart). Publishing and archiving are separate actions after creation. Until a dedicated publish action exists, `PUT /products/{id}` still takes an optional `status` (`draft` or `active`), and `POST /products/{id}/archive` archives.
- The service still accepts a status on create (the seed uses it to build demo products as active, archived and so on), only the HTTP body no longer does.

## D14 — One product shape
- Every endpoint that answers with a product returns the same JSON: list items, `POST /products` (JSON and multipart), `GET`, `PUT`, `POST /products/{id}/archive` and `PATCH /products/{id}/stock`. The stock endpoint used to return a separate stock level (`product_id`, `available`, `stock_label`, `updated_at`), so a client had two shapes to handle.
- The stock handler does not import `product`: `stock.NewHandler` takes a `Loader` (`productHandler.Load`, wired in `internal/app`) that returns the product after the change, rendered by the product feature. The stock change and the read are two statements; a concurrent edit in between shows in the answer, which is what the seller wants to see.
- `e2e/product_shape_test.go` checks that all these answers have the same field names, and that the stock answer equals `GET /products/{id}` byte for byte after a change.
- The stock level the endpoint used to return is gone from the code too (D16).

## D15 — Shop logo
- `PUT /shop` takes `multipart/form-data` like the product endpoints: the profile fields and a logo image in `logo`. A JSON request still works and never touches the logo. A logo is set and replaced, never removed: the first version had `remove_logo=true`, dropped because the task asks only to set a logo and no screen used it. `logo_url` is no longer an input (a `logo_url` in JSON is `400 invalid_body`, in multipart `400 validation_error`): the server writes it, so a client cannot store a URL of its own choosing, an external one or another shop's file. The column and the response field stay.
- All or nothing, in the shop service: fields are validated, then the logo is converted and stored, then the row is written. When the write fails the new file is removed; when it succeeds the old logo file is deleted (best effort). A request with a logo counts against the same per shop image limit; JSON edits do not.
- The shop feature does not import `upload`: it declares `LogoStore` (`Save`, `Remove`) and `internal/app/photos.go` implements it on `upload.Service`, like `PhotoStore` for products. The two adapters differ only in the error values they translate to.
- Multipart reading is shared: `httpx.ReadForm` applies the limits while reading (files, value size, body size), refuses unknown and repeated fields, and tells "list field not sent" from "sent empty". It also refuses a body that does not end with its closing boundary: Go's `multipart.Reader` reports a body cut between two parts as a normal end, which would apply a form with missing fields. `httpx/form_test.go` cuts a body at every byte. The product endpoints use the same reader.
- `POST /uploads` had no consumer after this and was removed (D16).

## D16 — No upload endpoint, no stock label
- `POST /uploads` is removed from the router, the spec and nginx. Images are saved only by `POST /products`, `PUT /products/{id}` and `PUT /shop` (D12, D15), and none of them accepts a URL, so the endpoint had nothing to feed. `internal/upload` stays as the service behind the two adapters in `internal/app/photos.go`: it converts and stores an image, and removes one. `GET /api/uploads/{shop_id}/{name}` is still served by nginx. `upload.Handler`, `Service.Open` and `Repository.Open` are gone (nothing read a file through the backend). The per shop limit `RATE_LIMIT_IMAGES_PER_MINUTE` stays: it limits the requests that save an image.
- `stock.Service.SetStock` returns only an error. `Level`, `Label`, `LabelFor`, the service threshold and the setting `LOW_STOCK_THRESHOLD` are removed: after D13 and D14 no response carries `available` or `stock_label`, so nothing used them. `stock.NewService` takes only the repository. A screen derives `available = stock - reserved` and its own low stock warning.
- The frontend's generated client has `POST /uploads`, `StockLevel` and `StockLabel` from an older spec; regenerating it (`npm run api:download` and `api:generate`) removes them, and the `StockLabel` type used by `entities/product` has to be declared in the frontend.

## D17 — Tokens of deleted accounts
- A token stays valid until it expires, so after a database reset it names a seller and shop that are gone: lists came back empty with `200` and every write was a `500` (a foreign key error). `auth.RequireLiveShop` runs after `RequireAuth` on every protected route and answers `401 unauthorized` when the seller and shop of the token do not exist together (`shops.id = shop_id AND seller_id = seller_id`), so the client signs in again. A shop that was found is remembered for 30 seconds, so it is not a query per request; one that was not found is checked every time. A failing check answers `500` and never lets the request through. Limit: it cannot tell an old token from a new one when a full reset gives the new seller the same ids; tokens are not bound to anything else.
- A sweeper that deleted image files nothing refers to was tried and removed: it cleaned up the leftovers of a crash between writing a file and saving its row, but it deletes files on a timer, and a mistake in it would delete live images. A leftover is a few hundred kilobytes, so they stay. If disk use ever matters, a manual command that lists them first is safer than a timer.
- The setting `RATE_LIMIT_UPLOADS_PER_MINUTE` is now `RATE_LIMIT_IMAGES_PER_MINUTE`: there is no upload endpoint any more, it limits the requests that save an image. Rename it in a local `.env` if it was set.

## D18 — Real-time order changes
- Sellers get new orders and status changes as they happen. Transport: Server-Sent Events, `GET /orders/events`, `text/event-stream`, authenticated like every protected route. Events: `order.created` (the order summary, as in `GET /orders`) and `order.status_changed` (id, number, status, `status_changed_at`). Events carry only data of the caller's shop.
- Fetch, not `EventSource`: the browser's `EventSource` cannot send an `Authorization` header, and a token in the URL would end up in logs. The frontend reads the stream with `fetch` and a `ReadableStream`.
- Publish after commit: the order service publishes an event only after `InTx` succeeds, so a rolled-back change is never announced. The publisher is an interface declared in `order`, implemented by an in-process hub in `internal/realtime`. Feature packages do not import each other's concrete types.
- Hub: one subscriber list per shop. Each subscriber has a small buffer. A subscriber whose buffer is full is dropped and its stream closed, so one slow client cannot block a publish. The client then reconnects and refetches the list; nothing is replayed, so no event log is kept.
- Heartbeat: a comment line every 25 seconds keeps proxies from closing an idle stream.
- Limits: at most 5 open streams per shop; the sixth gets `429 rate_limited`. The stream ends when the token expires, and the client reconnects with a fresh token. The stream counts once against the per-shop limiter, when it opens.
- nginx: the `/api/orders/events` location turns off `proxy_buffering`, disables gzip and sets a read timeout longer than the heartbeat.
- Why SSE and not polling or WebSocket: it is the fastest option that fits the need. The server pushes, the client only reads, and SSE reconnects by itself. Polling would wait up to a polling interval. WebSocket adds a library and an origin check for a direction nobody uses.
- Scope for now: one backend instance, which matches D21. Moving to several instances means replacing the in-process hub with Postgres `LISTEN/NOTIFY` behind the same interface; the endpoint and the events stay the same.
- Later, not in this decision: a Telegram message for each `order.created` to a seller who linked a chat (D21). It subscribes to the same hub and is its own issue.
- Considered: polling every few seconds (simplest, but slower and more requests), WebSocket (two-way channel nobody needs), `LISTEN/NOTIFY` from the start (more moving parts for one instance).

## D19 — Telegram alert for each new order
- When a buyer's order is created, the seller's linked Telegram chat (D21) gets one message in Russian, like the panel: order number, time in the business time zone, buyer name, the first 10 items with quantity and price, the total, and a reminder to open the panel. Nothing is sent for other events or for sellers without a linked chat. The text is Telegram HTML and every value from data is escaped, so a name or a title cannot add a link. If the items cannot be read, the message goes out without them.
- With `PANEL_URL` set, a button opens `/orders?order=<id>` in the panel. It is empty by default because there is no public address: on a local network it is the address of the machine that runs the panel.
- The alert is a second publisher next to the realtime hub (D18). `Publish` only puts the alert on a queue of 100, so a slow Telegram never delays the request that created the order. One worker sends the queue in order. A full queue drops the alert and logs it.
- No retries. A failed send is logged with the order number and not sent again, because a retry after a timeout could send the same message twice and the seller can always see the order in the panel.
- The message contains the buyer's name, the items and the total, which the seller already sees in the panel. The buyer's phone and address are not sent.
- Only one backend instance sends alerts (D21 polling). With several instances, the queue would live in each and alerts would double; the same switch to a shared bus as D18 solves both.

## D20 — A product always has a photo, the category filter covers subcategories
- The task asks for at least one photo, so `POST /products` refuses a product without one and `PUT /products/{id}` refuses to leave none. A create is therefore always `multipart/form-data`, a JSON body gets `400 validation_error`, and every create counts against the image rate limit. A JSON edit still works and keeps the photos.
- Products saved before this rule have no photo: they can be read, sold and archived, and the next edit has to add one. The seed gives every demo product a freely licensed photo of its type, embedded in the binary (`backend/internal/seed/photos`, sources in `SOURCES.md`), and a one colour image where there is none.
- `GET /products?category=` returns the category and all its subcategories, so filtering by a top category such as Electronics finds the phones.
- Considered: asking for a photo only when a draft is activated (a product could be created in one JSON call, but the catalogue would hold products without photos), a database constraint (a row count across two tables needs a deferred trigger, the service rule is enough), filtering by the exact category only (a top category looked empty).

## D21 — Sign-in with a Telegram code
- Numbered D13 until 25 November, when the number turned out to be used twice.
- A seller links a Telegram chat once: `POST /auth/telegram/link` (signed in) returns a `t.me` link with a one-time token valid 10 minutes. Opening it sends `/start <token>` to the bot, which stores the chat on the seller. The token is stored only as a SHA-256 hash and is deleted when used.
- Sign-in: `POST /auth/request-code` sends a 6-digit code to the linked chat as tap-to-copy text (`<code>`, valid 5 minutes, one code per cooldown of 60 seconds, stored as a hash; a request inside the cooldown answers `429 rate_limited` with `Retry-After`). `POST /auth/verify` returns the same `TokenResponse` as password login. A code works once and stops working after 5 wrong attempts. Verification is guarded like login (5 failures per IP and email in 15 minutes). Saving a code, counting a try and using a code are single SQL statements, so parallel requests cannot get more messages, guesses or tokens. A code with no tries left stays until the cooldown lets a new one replace it, so using up the tries never skips the wait. A code Telegram does not accept is deleted and the answer is `503 telegram_send_failed`.
- Without a linked chat, `request-code` answers `409 telegram_not_linked`, for an unknown email and for a known seller alike. The callers learn that a code cannot be sent, not whether the account exists. It does reveal whether an email has a linked chat, so the request-code limit (5 per IP and email in 15 minutes) stays. Without `TELEGRAM_BOT_TOKEN` the two endpoints return `503 telegram_unavailable`, and password login is unaffected.
- Changed: the first version answered `202` for every email and sent nothing when there was no chat, so the UI could not tell the user why no code came. The silent answer is gone; the reason is in the answer now.
- The bot gets updates by long polling (`getUpdates`) inside the backend process, so one backend instance must run per bot. Several instances would fight over updates. Switching to a webhook is the way to scale out.
- Why: it reverses the D2 trade-off without an SMS provider. Telegram is already the team's channel, costs nothing, and a bot can deliver codes. Password login stays so a seller who has not linked yet is not locked out.
- Considered: SMS codes (needs a paid provider, and phone numbers must be verified), email codes (needs an SMTP service, and the email is already the login name), TOTP apps (the seller must set up an app, more friction for a shop owner), and a webhook instead of polling (needs a public HTTPS address, which the MVP deployment does not have).
- Trade-off: the code is sent in plain Telegram chat and the seller must keep access to that account. A stolen Telegram account can sign in, which is why password login remains available and a relink replaces the chat.
